# 响应式布局方案：以「连续函数」适应不同分辨率与缩放

## 背景问题

同一份界面在两台电脑上显示效果不同：

- 都是 **1920×1200** 物理分辨率
- 一台 Windows 缩放 **125%**，另一台 **150%**

原因：CSS 的 `px` 是**逻辑像素**，浏览器视口宽度 = 物理分辨率 ÷ 缩放比。

| 物理分辨率 | 缩放 | 浏览器视口（CSS px） |
| --- | --- | --- |
| 1920 | 125% | 1920 ÷ 1.25 = **1536** |
| 1920 | 150% | 1920 ÷ 1.50 = **1280** |

也就是说：**分辨率、系统缩放、浏览器缩放（Ctrl±）、窗口拖拽**，最终都折算成同一个变量——**CSS 视口宽度**。

早期布局把列宽写死成固定像素（如 `264px + 340px`），在窄视口（1280）上占比过大、详情栏被挤，界面失衡。

## 核心思路：把列宽变成「可用宽度的连续函数」

不写任何 `if 150% then ...` 的分支，而是让列宽随可用宽度**平滑连续地**取值。这样任意缩放、任意分辨率都落在同一条曲线上，**新机器无需改代码**。

实现工具：**Tailwind 断点** + CSS **`clamp(min, 视口比例, max)`**。

### 关键代码

文件：`frontend/src/features/recipes/RecipesPage.tsx`

```tsx
<div className="grid h-full min-h-0 grid-cols-1
  md:grid-cols-[clamp(300px,32vw,340px)_minmax(0,1fr)]
  lg:grid-cols-[clamp(210px,17vw,264px)_clamp(300px,24vw,360px)_minmax(0,1fr)]">
```

- `clamp(min, vw, max)`：下限保证不过窄，`vw` 让列宽随视口连续伸缩，上限防止过宽。
- `minmax(0,1fr)`：详情栏占剩余空间，`0` 下限保证能正确收缩、内容不外溢。
- 中间列表 `<section>` 加 `min-w-0`，配合项内 `line-clamp-2` / `truncate`，长文本一律截断，不会反向撑宽列。

### 断点行为

| CSS 视口宽度 | 断点 | 布局 |
| --- | --- | --- |
| < 768px（手机 / 小窗） | base | 单栏；底部导航；列表与详情按选中切换全屏 |
| 768–1023px（平板 / 半屏） | md | 两栏：列表 `clamp(300,32vw,340)` + 详情；分类改为顶部横向标签条 |
| ≥ 1024px（笔记本 / 桌面） | lg | 三栏：分类 `clamp(210,17vw,264)` + 列表 `clamp(300,24vw,360)` + 详情 `minmax(0,1fr)` |

### 效果验证（两个目标视口）

| 视口 | 分类侧栏 | 列表栏 | 详情栏（剩余） |
| --- | --- | --- | --- |
| 1280（150% 那台） | 217px | 307px | 680px |
| 1536（125% 这台） | 261px | 360px | 839px |

两台机器比例合理，详情栏不再被挤。

## 覆盖范围与边界

### 已通用覆盖（宽度这一轴）

- 任意**分辨率**：1366×768、1920×1080、2560×1440、4K 等。
- 任意**缩放**：100% / 125% / 150% / 175% / 200% …
- 浏览器缩放、窗口拖拽。
- 超宽 / 4K：列表与侧栏有 `clamp` 上限；详情内容有 `mx-auto max-w-3xl`（≈768px 居中），不会拉成超长行。

### 尚未完全覆盖的独立维度（非「更多分辨率」，而是别的坐标轴）

| 维度 | 状态 | 说明 |
| --- | --- | --- |
| 用户放大**基础字号**（无障碍） | ⚠️ 部分 | 关键宽度用 `px`/`vw` 而非 `rem`，字号变大时列宽不跟随 |
| 超宽屏详情两侧留白 | ⚠️ 取舍 | 内容锁 `max-w-3xl` 居中，阅读体验好但不铺满 |
| 极端宽高比 / 折叠屏 | ✅ | 单栏降级 |
| 内容长度（超长标题/来源） | ✅ | `min-w-0` + 截断 |

## 从根上减少「未来新情况」的原则

1. **相对单位优先**：关键尺寸尽量用 `rem`（跟随字号）而非 `px`。
2. **容器查询（container queries）**：让组件按**自身容器宽度**自适应，而非全局视口——组件放哪儿都对。
3. **按比例 / `minmax` 思考**，避免任何写死的绝对像素。
4. **宽度矩阵测试**：一次性覆盖 360 / 768 / 1024 / 1280 / 1536 / 1920 / 2560，验证整条曲线，而非「报一个修一个」。

> 结论：`clamp()` + 断点在「宽度」这一轴上是**通用连续解**，不是单点补丁；要进一步减少意外，可推进 `rem` 化与容器查询的系统性改造。

# 第二轮：为什么「每加一个新功能就复发」，以及根治

## 复现的症状

第一轮的 `clamp()` 栅格上线后，**导出（Export）功能**又在 150% 那台机器上出问题：选择模式的操作条（`0 selected / Select all / Clear / Export`）在窄列里 `flex-wrap` 意外换行，Export 被挤到第二行、还带着 `ml-auto` 右贴，观感失衡。换成别的新功能也会时不时重演。

**这不是新 bug，是同一类 bug 换了个功能又长出来。**

## 关键认知修正：这从来不是「DPI / scale 问题」

把「两台电脑不一样」重新翻译成一句话：**150% 只是让 CSS 视口更窄**（1920@125%=1536，1920@150%=1280）。DPI、系统缩放、浏览器 Ctrl±、拖窗口，最后都折算成同一个变量——视口宽度。

所以每一次这类报告，都应按**普通的窄视口响应式问题**处理，而不是去想「怎么适配缩放」。最便宜的一招随之而来：**窄端优先（narrow-first）**——先在 1280 做对，1536 自然成立。之前一直在自己的 1536 上开发、肉眼看着好就收工，从没在 1280 看过，这是复发的直接原因。

## 复发的真正根因：三层里只补了第一层

| 层 | 第一轮状态 | 后果 |
| --- | --- | --- |
| ① 全局栅格 | ✅ `clamp()` 断点 | 列宽是连续的 |
| ② 组件内部 | ❌ 每个新功能手写 flex 行、按**全局视口** `md/lg` 判断 | 组件不知道**自己那一列**多宽，窄列就崩 |
| ③ 发布前关卡 | ❌ 只在 1536 肉眼看 | 1280 的问题没人拦，上线才发现 |

「每次手修实例」只在打补丁；②③ 不补，同类 bug 必然随新功能反复出现。

## 改进 A：组件按「自身容器」自适应（容器查询）

用 **Tailwind v4 原生容器查询**（无需插件）把响应式行为下沉到组件自身：给面板/列容器加 `@container`，内部用 `@sm:`/`@md:`/`@[Npx]:` 按**容器自己的宽度**响应，而不是全局视口 `md:/lg:`。这样同一个组件放进 307px 的列会自动堆叠、放进更宽的容器会平铺，**与机器/缩放无关，也与它被放在哪一栏无关**。

落地示例——`frontend/src/features/recipes/RecipesPage.tsx` 的列表 `<section>`：

```tsx
<section className="@container relative flex min-h-0 min-w-0 flex-col ...">
  ...
  {selectMode && (
    <div className="mt-2 flex flex-col gap-2 @sm:flex-row @sm:items-center">
      <div className="flex items-center gap-2">
        <span>… selected</span><Button>Select all</Button><Button>Clear</Button>
      </div>
      <Button className="w-full @sm:ml-auto @sm:w-auto">Export</Button>
    </div>
  )}
</section>
```

- 默认（窄列，本项目列表列 ~300–360px 的常态）：计数/操作在一行，**Export 整行置底**——确定性、有意为之，不是 `flex-wrap` 的意外换行。
- `@sm`（容器 ≥ 384px）：自动流成单行，Export 右贴。

**规则：以后所有「工具栏 / 操作条 / 卡片内排布」都用容器查询，不用全局 `md/lg` 去猜列宽。**

## 改进 B：一道「宽度矩阵」发布前关卡（dev-only）

新增仅开发环境挂载的路由 **`/dev/widths`**（`frontend/src/features/dev/WidthMatrixPage.tsx`，由 `import.meta.env.DEV` 守卫）。它把任意 app 路径塞进一排 iframe，同屏并列渲染 **360 / 768 / 1024 / 1280 / 1536 / 1920** 六个宽度。每个 iframe 是独立浏览上下文，容器查询/媒体查询按 iframe 宽度求值。

- 用法：启动 dev → 登录 → 打开 `/dev/widths` → 点预设或输入路径。
- **每加完一个 UI，在这里扫一眼 1280 再收工。整条曲线一屏看完，不需要第二台电脑。**

## 尚未做、但方向明确的加分项

- 关键尺寸 **rem 化 + 设计 token**：让间距/字号成体系，减少「某个缩放刚好卡在断点边缘」的意外。属独立改造，与本轮修复分开排期。

## 一句话总结这一轮

把「每次手修实例」换成：**认知（当成窄视口问题、窄端优先）+ 默认写法（容器查询，组件自适应）+ 关卡（`/dev/widths` 宽度矩阵）**。新功能天生就对，而不是靠事后补。
